# Задача бэклога командой ролей

Работаем как команда из шести ролей (раздел 1 бэклога), а не один исполнитель. Исполнитель пишет код; роли из `.claude/agents/` — ревьюеры: `product-analyst`, `ux-designer`, `frontend-lead`, `backend-lead`, `devops-sre`, `qa-lead`.

## 0. Подготовка

1. Прочитай `AGENTS.md` и в `docs/team/2026-10-15-team-and-backlog.md`: строку задачи (разделы 3 и 7), решения владельца (раздел 4 — не обсуждаются заново), ограничения среды (0.1), ворота (6).
2. `git status --short` — чужие незакоммиченные изменения сохраняй и не включай в свой коммит.
3. Определи роль-владельца задачи по префиксу ID и смежные роли:

| Что меняется | Ревью обязательно |
|---|---|
| Интерфейс, тексты, стили | `ux-designer`, `frontend-lead` |
| `frontend/` код | `frontend-lead` |
| `backend/`, SQL, миграции | `backend-lead` |
| `contracts/` или ответ API, который читает клиент | `backend-lead` и `frontend-lead` |
| `infra/`, `.github/`, `docs/operations/` | `devops-sre` |
| Новый пользовательский сценарий (T-xx) | `product-analyst` (спецификация и приёмка) |
| Любая задача | `qa-lead` (ворота перед коммитом) |

## 1. Спецификация (для T-xx, UX-xx с новым экраном и всего, что меняет поведение для пользователей)

1. Субагент `product-analyst` пишет сценарии по ролям, объём и критерии приёмки; `ux-designer` — экран словами, состояния, мобильную версию 390 px, тексты по словарю. Для технического долга (FE/B/Q/INF без видимых изменений) достаточно абзаца «что и зачем» в отчёте — спецификация не нужна.
2. Файл `docs/superpowers/specs/<ГГГГ-ММ-ДД>-<тема>.md`: проблема, сценарии, что не входит, API/данные на уровне потребности, состояния, критерии приёмки, **открытые вопросы владельцу с рекомендацией** по каждому.
3. Покажи владельцу вопросы (коротко, с рекомендацией первым вариантом) и дождись ответа. Пока ждёшь — бери другую задачу, не начинай код этой. Ответ впиши в спецификацию («Решения владельца, дата»).

## 2. Код по контракту

1. Порядок: контракт `contracts/openapi.yaml` → `npm.cmd --prefix frontend run api:generate` (в NTFS-копии, схему не править руками) → backend (миграция только новым файлом `V<N+1>__*.sql`) → frontend.
2. Тесты рядом с кодом: backend HTTP-тест с 400/401/404 и чужим workspace; Angular `*.spec.ts`, включая сброс при смене аккаунта; UI/real сценарий для нового экрана.
3. Для исправления дефекта — сначала падающий тест (RED), потом исправление (GREEN).
4. Правки файлов с CRLF — без смены переводов строк (Python с `newline=''`); длинные Bash heredoc (больше ~8 КБ) не используй — пиши файлы инструментом Write/Edit.
5. Форматирование: правь формат только в своих строках и новых файлах; массовое переформатирование — отдельный style-коммит.
6. Изменилась карта проекта (новый модуль, точка входа, команда) — обнови `AGENTS.md`.

## 3. Ревью смежных ролей

1. Запусти нужных субагентов из таблицы параллельно, передав: ID задачи, ссылку на спецификацию, `git diff` или список файлов, числа прогонов.
2. UX-ревью интерфейса — по скриншотам 1280 и 390 px, если их можно снять (UI-фикстуры или real lane); иначе в строке раздела 0 честно «по коду, скриншоты не снимались».
3. Каждое замечание: исправить и перепроверить, либо явно оставить открытым с причиной в строке раздела 0. Повторное ревью после существенных исправлений.

## 4. Ворота QA

Прогон по скиллу `ntfs-checks` в NTFS-копии, минимум по чек-листу агента `qa-lead`, затем сам `qa-lead` подтверждает: числа было/стало, что не запускалось и почему.

## 5. Коммит и запись

1. Один коммит на задачу: `<ID>: <что сделано по-английски в повелительном наклонении>`, тело — кратко что и почему, в конце строка соавторства из системных указаний. В коммит только файлы задачи.
2. Строка в таблицу раздела 0 бэклога: дата, «Волна N, ID (роль): что сделано. Проверка: числа. Смежное ревью: роли и итог. Открыто: …», коммит — короткий хэш (если строка добавляется тем же коммитом — «в этом коммите», иначе отдельный docs-коммит с хэшем).
3. Если задача снята или перенесена — строка с причиной вместо кода.
4. Push, релиз в кабинет и любые действия с рабочим контуром — **только по отдельной команде владельца** (скилл `release-cabinet`).

## Запрещено

- Читать `compose.env`, `private/`, `data/`, резервные копии; запускать compose против проекта `mentor-platform`.
- Класть в репозиторий секреты, реальные имена учеников, абсолютные пути с именем пользователя (используй относительные пути и `%LOCALAPPDATA%`, `%USERPROFILE%`).
- Переписывать применённые миграции, править `schema.d.ts` руками, отключать проверки, чтобы пройти ворота.
