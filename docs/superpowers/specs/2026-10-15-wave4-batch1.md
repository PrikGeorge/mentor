Общие правила для всех пяти задач:

- Словарь: «занятие» (не урок), «домашняя работа» (в подписях — «ДЗ» только в узких колонках), «наставник» в текстах ученику, «Вы» — преподавателю, ученику — «ты». Время всегда с «МСК», даты `дд.мм.гггг`, в узких местах `дд.мм`.

- Предпросмотр «Экран ученика» у преподавателя остаётся только для чтения.

## T13. Текстовая сдача ДЗ без файла (S)

**Сценарий.** Ученик решил небольшую задачу и не хочет создавать файл: вставляет код или ответ прямо в форму. Наставник видит работу как обычную однофайловую сдачу: «Открыть код и прокомментировать», комментарии к строкам, ревью, оценка. Администратор не участвует.

**Экран** (`homework-page`, блок «Сдать домашнюю работу», только ученик):

- Над полем файла — переключатель из двух кнопок (`role="radiogroup"`, стиль вкладок `.tabs`): **«Файл»** | **«Текстом»**. По умолчанию «Файл»; выбор не запоминается.
- Режим «Текстом»:
  - Поле «Ответ» — `textarea` моноширинным PT Mono, 14 строк, `spellcheck=false`, Tab не перехватываем (доступность).
  - Под полем выбор формата: «Код Java» / «Текст или Markdown». Подсказка: «Сохранится как файл MyClass.java — наставник сможет прокомментировать строки.» (имя пересчитывается на лету).
  - Счётчик «12,4 КиБ из 256 КиБ» (байты UTF-8).
  - Поля «Репозиторий» и «Комментарий к работе» общие для обоих режимов.
- Кнопка та же: «Отправить на ревью».

**Как устроено.** Браузер собирает из текста файл и отправляет тем же `POST …/homework` (multipart). Имя: для Java — имя первого `public class|record|interface|enum X` → `X.java`, иначе `Main.java`; для текста — `answer.md`. **Контракт и backend не меняются**: проверки имени, размера, идемпотентности (Idempotency-Key на попытку) и просмотр `.java/.md ≤ 256 КиБ` уже есть.

**Граничные случаи.**

- Пустой текст или только пробелы → под полем «Напиши ответ или переключись на файл.»
- Больше 256 КиБ → «Ответ больше 256 КиБ. Сдай его файлом или архивом.» (лимит текста, а не 20 МиБ файла, чтобы работу всегда можно было открыть и прокомментировать).
- Переключение режима не стирает введённое в другом режиме, но отправляется только активный.
- После успешной отправки текст очищается (как UX-09); «результат неизвестен» → повтор с тем же ключом, текст не меняется.
- Текст не сохраняется в `localStorage` и не переживает перезагрузку (FE-07: приватный код не кладём в браузерное хранилище). Если поле не пустое, при уходе со страницы ничего не спрашиваем — это осознанное упрощение, его можно вернуть отдельной задачей.
- Ученик в архиве / предпросмотр — формы нет, как сейчас.

**Тесты.** Unit: имя файла по классу, лимит байтов, очистка, ключ идемпотентности, переключатель. UI-fixture: отправка текстом → multipart с `Main.java`. Backend — без изменений.

## T04. Расписание преподавателя «Сегодня / Неделя» (M)

**Сценарий.** Преподаватель утром открывает «Расписание» и видит занятия всех активных учеников на сегодня, затем листает неделю. Ученик и администратор этот экран не видят (у ученика остаются «Главная» и «Занятия»).

**Экран** — новый маршрут `/teacher/schedule`, пункт шапки **«Расписание»** рядом с «Мои ученики» (ленивый чанк). Стартовая страница преподавателя не меняется.

- `page-head`: заголовок «Расписание», подзаголовок «Время по Москве. Ученики в архиве не показываются.»
- Переключатель `.tabs`: **«Сегодня»** | **«Неделя»**; для недели — «← Прошлая неделя», «Эта неделя», «Следующая →», подпись «13–19 октября 2026». Выбор держится в query `?view=week&from=2026-10-13`, чтобы работали «Назад» и ссылка.
- Строка занятия (общий шаблон для обоих видов, на мобильном складывается в карточку):
  `18:00–19:00` · аватар-инициал и **имя ученика** · «№ 7 · Тема занятия» (ссылка на страницу занятия) · тег статуса (`Запланировано / Подготовлено / Проведено`) · тег **«Идёт сейчас»** (`.tag.on`) для текущего · кнопка «Открыть».
- «Неделя» — секции по дням `h2` «Понедельник, 13 октября», сегодняшний день помечен «сегодня»; пустые дни показываются одной строкой «Свободно».
- Пустой «Сегодня»: «Сегодня занятий нет.» + ссылка «Посмотреть неделю →». Пустая неделя: «На этой неделе занятий нет.»
- Ошибка — общий `mentor-error-banner` с «Повторить загрузку».

**Контракт.** Новый `GET /api/v1/workspaces/{workspaceId}/schedule?from=YYYY-MM-DD&to=YYYY-MM-DD` (включительно, не больше 31 дня, `from ≤ to`, иначе 400). Ответ `{ from, to, items: ScheduleItem[] }`, где `ScheduleItem` = поля `LessonSummary` + `studentName`. Сортировка по дате, времени, `createdAt`, id. Без пагинации (диапазон ограничен). Права: только преподаватель этого workspace (`WorkspaceAccess.requireTeacher`); ученик, администратор и чужой преподаватель — 404/403 по общему правилу. Только активные карточки. Реализация — один SQL в `LessonRepository` по индексу `lesson_order`/новому индексу `(workspace_id, local_date)` в той же миграции V16, если план запроса этого потребует (проверим EXPLAIN на синтетике).

**Граничные случаи.** Занятие через полночь показывается в день начала. Смена часов на компьютере не влияет: «сегодня» считается по МСК. Номер занятия (`number`) — тот же, что на карточке.

**Тесты.** Backend: диапазон и валидация, изоляция workspace (чужие карточки с совпадающими ID), архив исключён, порядок. Unit: переключатель, неделя по МСК, «Идёт сейчас» на фиксированных часах. UI-fixture: навигация и пустые состояния. Real e2e: расписание в tenant-isolation (второй преподаватель не видит чужих занятий).

## T16. «Отметьте проведённым» и мягкая фраза ученику (S)

**Сценарий.** Занятие прошло, преподаватель забыл нажать «Проведено». Сейчас ученик видит на главной «Дата занятия прошла. Факт проведения здесь не отмечен.» — звучит как упрёк и раскрывает внутреннюю отметку. Нужно: преподавателю — напоминание с действием в один клик, ученику — нейтральный текст.

**Преподаватель.**

- Расписание (T04), вид «Сегодня»: над списком блок `.warning-banner` **«Отметьте проведённые занятия»** — до 5 прошедших (окончание < сейчас) неотмеченных занятий за последние 14 дней: «Михаил · № 7 · 14.10, 18:00» + кнопка **«Проведено»** (PATCH `conducted: true` с ревизией) и ссылка «Открыть». Если больше 5 — «Ещё N в неделе →». После отметки строка исчезает со статусом «Отмечено». Конфликт ревизии → «Занятие изменилось. Обновите расписание.»
- «Мои ученики»: одна строка `.callout` над очередью «2 прошедших занятия не отмечены проведёнными · Отметить →» (ведёт в расписание). Данные — тот же `GET /schedule` за 14 дней; если запрос упал, строка просто не показывается.
- Страница занятия: кнопка «Отметить проведённым» уже выделена для прошедших; добавляем подсказку рядом «Занятие прошло — отметьте, если оно состоялось.»
- 14 дней — чтобы не напоминать про импортированную историю старого кабинета, где отметки «Проведено» нет совсем.

**Ученик.**

- Главная, прошедшее неотмеченное занятие: «Занятие по расписанию уже прошло. Новое появится, когда наставник назначит дату.» (отмеченное — как сейчас: «Занятие проведено. Новое появится…»).
- Тег статуса у ученика для прошедшего неотмеченного занятия: вместо «Запланировано»/«Подготовлено» — нейтральный **«Прошло»** (`.tag.quiet`, иконка `calendar`). Преподаватель по-прежнему видит фактический статус. `lessonStatus` получает параметр зрителя; шапка занятия и таблицы используют его.

**Контракт.** Без изменений (используется `GET /schedule` из T04 и существующий PATCH).

**Тесты.** Unit: `lessonStatus` для двух зрителей и границы «окончание = сейчас», тексты главной, блок напоминаний (5 + «ещё N», конфликт). UI-fixture: отметка из расписания.

## T09. Срок сдачи ДЗ и подсветка просрочки (M)

**Сценарий.** Преподаватель при создании или правке занятия задаёт «Сдать ДЗ до 20.10, 23:59». Ученик видит срок на главной, в списке занятий и над формой сдачи. После срока без единой работы занятие подсвечивается: у преподавателя — «Просрочено на 2 дн.», у ученика — спокойнее. Поздняя сдача **принимается** всегда; срок ничего не блокирует.

**Что считается работой:** сданный файл/текст ДЗ или отправленная попытка упражнения с размещением «Домашняя работа» — то же определение хода, что в T02.

**Состояния срока** (считает сервер по своим часам):

| state | Условие | Преподаватель | Ученик |
|---|---|---|---|
| `open` | срок впереди, работ нет | «ДЗ до 20.10, 23:59» | «Сдать до 20.10, 23:59 МСК · через 2 дн.» |
| `overdue` | срок прошёл, работ нет | `.tag.danger` «Просрочено на 2 дн.» | «Срок был 20.10. Сдай, когда будет готово — наставник посмотрит.» |
| `onTime` | первая работа до срока | «Сдано в срок» (тихо) | «Сдано в срок» |
| `late` | первая работа после срока | «Сдано после срока» | «Сдано после срока» |

У архивной карточки `overdue` не подсвечивается (показывается просто срок).

**Экраны.**

- Форма занятия (`lesson-form`, создание и правка): необязательный блок «Срок домашней работы» — дата и время (по умолчанию 23:59), кнопка «Убрать срок». Подсказка: «Ученик увидит срок. Сдать работу можно и позже.» Срок раньше начала занятия — ошибка под полем «Срок не может быть раньше начала занятия.»
- Карточка ученика (таблица занятий у обеих ролей): в колонке «Дата и время» вторая строка срока; тег состояния — в колонке «Статус».
- Главная ученика: в `dl.sheet` строка «Сдать ДЗ до» для фокусного занятия.
- Домашняя работа: над формой сдачи строка срока; в истории у работы, сданной после срока, тихая пометка «после срока» (видна обеим ролям).
- Часы «чей ход» не меняются (вопрос 3 ниже).

**Контракт и данные.**

- `V16__homework_due.sql`: `ALTER TABLE lesson ADD COLUMN homework_due_at TIMESTAMPTZ;` (плюс индекс для T04, если понадобится). Старые занятия — без срока.
- Ввод: `LessonCreateInput` и `LessonMetadataInput` получают необязательное `homeworkDue: { date, time } | null` (МСК, как `date/time` занятия; `null` в PATCH снимает срок). Правка срока — обычная ревизия метаданных.
- Вывод: `TeacherLessonView`, `PublicLessonView`, `LessonSummary` (а значит и `dashboards`, `dashboard.focus`, `schedule`) получают необязательное `homeworkDue: { date, time, state }` — отсутствует, если срока нет. Первая работа считается в SQL одним подзапросом (MIN по сдачам и homework-попыткам), без N+1.

**Тесты.** Backend: валидация (дата, время, срок раньше начала, `null`), четыре состояния на фиксированных `Clock`, homework-попытка как работа, архив, PATCH-конфликт. Unit: тексты состояний и склонение «дн.», форма. UI-fixture: срок в таблице и над формой. Real e2e: срок задан → ученик видит «Сдать до».

## T05. «Создать занятие на основе…» (M)

**Сценарий.** У преподавателя есть удачное занятие (сценарий, задания, упражнения). Он хочет: (а) повторить его следующему занятию того же ученика или (б) провести то же занятие с другим учеником. Ученик видит новое занятие как обычное; он не узнаёт, что оно скопировано, и не видит ничего из чужой карточки.

**Экран.**

- Страница занятия, панель действий преподавателя: кнопка **«Создать на основе»** (иконка `copy`).
- Открывает ту же `mentor-lesson-form` в режиме копии: заголовок «Новое занятие на основе № 7», поле **«Ученик»** (`select` активных учеников, по умолчанию текущий), тема — копия темы, время и длительность — как у исходного, дата — сегодня по МСК. Блок «Что скопируется»: «Сценарий преподавателя · Задания ученика · Упражнения тренажёра: 3». Ниже тихо: «Материалы, работы, ревью, отметка «Проведено» и срок ДЗ не копируются.»
- После создания — переход на страницу нового занятия; `success-banner` «Занятие создано на основе № 7. Добавьте материалы, когда будут готовы.»

**Что копируется.** Тексты `teacherNotes` и `studentNotes` (видимость сохраняется: сценарий остаётся «Только вам»). Активные назначения упражнений с размещением и порядком — по текущей ревизии каталога; упражнение, которого больше нет в каталоге workspace, пропускается. **Не копируются:** `reviewNotes` (это итог конкретного занятия), материалы и комплект (статус нового занятия — «Запланировано»), работы, попытки, черновики, комментарии, «Проведено», срок ДЗ.

**Контракт.** `LessonCreateInput` получает необязательное `source: { studentId, lessonId }`. Создание и копирование — одна транзакция: блокировка целевой карточки, проверка, что исходное занятие в том же workspace и принадлежит этому преподавателю (иначе 404, без раскрытия существования), копия текстов и назначений. Целевая карточка в архиве — как обычное создание (по текущему правилу `lockTeacherCard`). Ответ — `TeacherLessonView` нового занятия.

**Граничные случаи.** Исходное занятие другого ученика того же workspace — можно; другого workspace — 404. Пустые тексты не создают пустых ревизий. Повторный клик не создаёт дубль (кнопка блокируется; идемпотентность POST занятия не вводим — занятие можно удалить, пока оно пустое).

**Тесты.** Backend: копия текстов/назначений/порядка, `reviewNotes` и материалы не копируются, пропуск удалённого упражнения, чужой workspace и чужие ID, ученик не может вызвать, транзакция откатывается целиком. Unit: форма в режиме копии, выбор ученика, текст «Что скопируется». Real e2e: копия занятия другому ученику — второй ученик видит задания, но не видит сценарий.

## Ревью и ворота по каждой задаче

- Бэкенд-лид: API, права workspace, SQL без N+1, миграция только новым файлом (T04, T09, T05).
- Фронтенд-лид: `SessionStore.generation`/`bound-scope` в новых страницах и формах, отмена запросов, ленивый чанк расписания.
- UX: «Партия», словарь, мобильная ширина 390, фокус и `aria` (переключатели, баннеры).
- QA: §6 — `schema.d.ts` + diff, backend verify, unit, build, lint, UI 4202, real e2e с tenant-isolation. Тренажёр и runner не меняются, `e2e:practice` не требуется.

## Вопросы владельцу

1. **T05, материалы.** Копировать ли файлы материалов? Рекомендация: нет в этой партии (нужна копия blob-объектов и решение про комплект/эталоны); если нужно — отдельная задача T05b.
2. **T04, место.** Отдельный пункт шапки «Расписание» (рекомендация) или блок «Сегодня» вверху «Мои ученики»?
3. **T09, часы.** Если срок задан и ход у ученика — считать ли на часах обратный отсчёт «до срока ДЗ» вместо «до занятия»? Рекомендация: пока нет, срок показываем строкой рядом; часы остаются про ход.
4. **T13, формат.** Достаточно ли «Код Java» и «Текст или Markdown» (рекомендация) — без нескольких файлов в одной текстовой сдаче?
5. **T16, окно.** Напоминать о неотмеченных занятиях за последние 14 дней — подходит?
