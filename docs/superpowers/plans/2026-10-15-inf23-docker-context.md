# INF-23 — закрытый контекст Docker по умолчанию

Владелец INF; смежные B/INF и QA. База `17e2555`. Один коммит без push. Рабочие конфигурация, данные и контейнеры не затрагиваются.

Персональные `Dockerfile.dockerignore` уже ограничивают три сервисные сборки. Корневой fallback исключает перечисленные каталоги и расширения, но неперечисленные файлы остаются доступны. Заменяем этот denylist корневым `.dockerignore` с `**` без исключений. Поддерживаемый BuildKit использует персональный allowlist; при его отсутствии контекст пуст и исходники не доступны для COPY. Подготовка учебных окружений создаёт отдельный минимальный временный контекст и от корневого файла не зависит.

Фактический тест обнаружил повторное разрешение всего поддерева через `!directory/` в персональных профилях: backend/runner `src/test` и лишний `target`, frontend лишний `dist/mentor` и `infra/proxy`. В этой задаче добавлены шесть исключений содержимого перед узкими разрешениями нужных подкаталогов/файлов. Для каждой находки — canary и реальный RED до исправления; границы изменения следуют результатам BuildKit и смежного ревью.

- [x] Реальный тест BuildKit только на собственных синтетических файлах: пустой root fallback, три персональных профиля с нужными source/prebuilt файлами, исключение canary из private/data/.runtime/.git/legacy/backup/config.
- [x] Заменить root denylist на deny-all; явно требовать BuildKit в эксплуатации и использовать `docker buildx build --load` в примерах.
- [x] Запуск проверки контекста в Linux CI до сборок; исключить её из Windows mock job.
- [x] RED → GREEN, parser/YAML/diff; B/INF и QA-ревью, карта и строка §0, коммит.

Основание поведения: [Docker build context](https://docs.docker.com/build/concepts/context/#dockerignore-files): персональный ignore имеет приоритет над корневым, правила не объединяются. Проверка использует `FROM scratch`, `COPY` и local export; не запускает контейнеры и не собирает приложение. Открытые image remediation, Q-18 snapshot, runner daemon и practice fixture сохраняются.
