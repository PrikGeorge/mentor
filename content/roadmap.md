# Маршрут до карьерного трека

Версия 27.09.2026. Это предлагаемый маршрут под подтверждённые 5–9 часов самостоятельной работы и два часовых урока в неделю. Исходный план пользователя остаётся исходным; пройденные темы не назначаются по датам.

## Что зафиксировано на скриншотах

- 09–29 сентября: Java Core, включая generics, enum/records, IO/NIO, Stream/Optional, даты, чистый код, HTTP.
- 30 сентября – 13 октября: алгоритмы, от Big-O и массивов до деревьев, динамики и графов.
- 14 октября – 12 декабря: Spring/DI; SQL/JDBC; JPA; Spring Data; REST; тестирование; Docker; Security/JWT, миграции, логирование; работа с ИИ.
- 13–26 декабря: Kafka, producer/consumer, доставка, идемпотентность, Compose и два сервиса.
- 06 декабря: крайний срок записи в карьерный трек. Это происходит раньше окончания Spring и Kafka; запись не должна ждать завершения всех технологий.

## Что предлагаю изменить

До 6 декабря остаётся примерно 10 учебных недель: 20 часов встреч и 50–90 часов самостоятельной работы. Поэтому обязательный результат — небольшой работающий backend, базовый SQL, проверки и объяснение своего кода. Расширенный стек добавляется после достижения этого результата.

JUnit вводим на текущих ошибках Library, а не откладываем до ноября. Git, чтение stack trace и README используем с первой недели. SQL изучаем до JPA. Простой HTTP-контроллер — до сложных связей сущностей. Миграции — вместе с первой постоянной БД. Алгоритмы повторяем небольшими задачами каждую неделю.

Kafka, LLM API, сложную динамику, собственную JWT-инфраструктуру и многосервисную архитектуру не включаем в обязательный минимум до 6 декабря. Для алгоритмически интенсивного отбора нужен дополнительный отдельный цикл; две недели календарного знакомства с графами не равны готовности к такому интервью.

## Недельная нагрузка

Обязательные 5 часов: 2 часа основной практики, 1 час исправлений/проверок, 1 час чтения и повторения, 1 час коротких задач/устной защиты. При наличии ещё 4 часов — углубление и дополнительный вариант, а не вторая обязательная домашка. Если первая задача заняла весь бюджет, следующая переносится с фиксацией причины.

Понедельник: разобрать затруднение и освоить один приём. Пятница: проверить перенос навыка на новые данные, защитить ДЗ, наметить следующий шаг. Каждый урок — 60 минут.

## 28 сентября – 4 октября: довести поиск до проверяемого состояния

Первый разбор (неизменяемые списки, группировка по ID, один живой фикс в Library) перенесён на **воскресенье 27.09, 12:00–13:00 по Москве** по указанию Георгия. Содержание возможной встречи в понедельник 28.09 определяется по результату этого урока; полная домашка на 3–3,5 часа к понедельнику автоматически не назначается. Пт 02.10: планируется защита поиска; воспроизводимый тест, основы JUnit на одном знакомом сценарии. Если группировка ещё не ясна, разбираем её вместо увеличения количества новых тем.

Результат недели: поиск с фильтром не падает, null имеет заданный смысл, есть проверки результата и исходного каталога. Один новый пример ученик объясняет без готового решения.

## 5–11 октября: целостность, контракты, коллекции

Пн 05.10: `bookId → вхождения → читатели`, разные типы ошибок, сортировка. Пт 09.10: защита validator; список причин отказа и конфликт ID. По одной короткой задаче на Map/Set и оценку сложности. В этом блоке проверяем Git-ветку, diff и понятные коммиты.

Результат: обязательные четыре задания Library приняты; ученик сам добавил регрессионные тесты и объясняет, почему множество читателей не считает все вхождения книги.

## 12–18 октября: SQL и граница приложения

Пн 12.10: таблицы book/reader/loan, PK/FK, SELECT/WHERE/JOIN на маленьком наборе. Пт 16.10: GROUP BY и LEFT JOIN, ручные HTTP-запросы и статусы; короткая демонстрация JDBC.

Результат: пять запросов с объяснением на данных с повторяющимися названиями и читателями без выдач; понимание, где заканчивается хранение и начинается бизнес-правило. Если Core не принят, часть урока остаётся на его защиту.

## 19–25 октября: первый REST API

Пн 19.10: DI на существующем сервисе, минимальный Spring Boot. Пт 23.10: чтение каталога и выдача через контроллер, DTO, валидация, единая ошибка.

Результат: API работает пока с памятью; бизнес-логика не переезжает в контроллер; обычный запрос и отказ проверяются отдельно. Глубокая настройка контейнера Spring в этот этап не входит.

## 26 октября – 1 ноября: PostgreSQL

Пн 26.10: схема и первая миграция, конфигурация подключения. Пт 30.10: небольшой JDBC/JdbcTemplate-репозиторий, параметры запроса, сохранение после перезапуска.

Результат: один вертикальный сценарий проходит HTTP → сервис → БД; чужие данные не подменяются в тестах и не зависят от порядка запуска.

## 2–8 ноября: JPA и транзакции

Пн 02.11: сопоставить известный SQL с JPA, связи и границы транзакции. Пт 06.11: выдача «всё или ничего» в БД; сравнить rollback с прежними проверками в памяти.

Результат: ошибка в выдаче нескольких книг оставляет БД без частичной выдачи. Ученик объясняет связь экземпляра, читателя и активной выдачи; pagination не теряет total.

## 9–15 ноября: проверки и конкуренция

Пн 09.11: unit vs integration, один тест с реальной тестовой БД; изоляция данных. Пт 13.11: два запроса на один экземпляр, ограничение БД/блокировка, базовое отличие потоков и процессов. На этом примере раскрываем race condition, не весь курс многопоточности.

Результат: тесты воспроизводимы из чистого состояния; один экземпляр нельзя одновременно выдать двум читателям. Если настройка Testcontainers мешает основному заданию, используем отдельную тестовую БД и явно описываем ограничения.

## 16–22 ноября: воспроизводимый запуск и защита

Пн 16.11: Docker Compose, конфигурация через окружение, миграции. Пт 20.11: полный демонстрационный сценарий, логирование ошибки, ревью README; первая 20-минутная учебная секция интервью.

Результат: другой человек запускает проект по README и проходит happy path и отказ. При отставании приоритет — этот результат, расширение стека переносится.

## 23–29 ноября: портфолио и пробное собеседование

Пн 23.11: защита проекта и изменение небольшого требования в прямом эфире. Пт 27.11: Java/SQL/HTTP, разбор ошибок и резюме на подтверждённых фактах.

Результат: рабочий проект, честное описание роли, список сильных/слабых тем. Базовые роли доступа добавляем только при готовом основном сценарии; JWT не обязателен для этого учебного MVP. Без авторизации сервис не позиционируется как готовый к публичному использованию.

## 30 ноября – 6 декабря: готовность к следующему этапу

Пн 30.11: повторная защита слабых мест. Пт 04.12: финальная проверка README, демонстрации, тестов и анкеты карьерного трека. До вс 06.12: Георгий/ученик выполняет запись и сообщает результат.

Минимальный комплект: резюме без выдуманного опыта, ссылка на воспроизводимый проект, история исправлений, результаты двух пробных секций интервью, понятный план оставшихся пробелов. Если проект ещё не готов, запись в карьерный трек обсуждается по его правилам; не отмечаем техническую готовность автоматически.

## После 6 декабря

Продолжаем повторение и работу с откликами. Kafka можно использовать для уведомления о выдаче/возврате после готовности базы: сначала событие и consumer, затем повторная доставка и идемпотентность. SQL/JVM/многопоточность и алгоритмы расширяем по конкретным собеседованиям. Даты 13–26 декабря — исходное окно пользователя, а не обязательство закрыть тему независимо от результатов.

## Контрольные переходы

Переход к Spring: ученик воспроизводит ошибку, исправляет её, пишет проверку и объясняет коллекции. Переход к ORM: самостоятельно читает JOIN и понимает ограничения БД. Выход на технические интервью: запускает и защищает проект, решает небольшую новую задачу, разбирает SQL и HTTP. Пропущенный критерий переносит объём, а не увеличивает обязательные часы.
