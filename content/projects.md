# Учебные проекты

Версия 27.09.2026. Это задания для ученика и критерии проверки, а не готовые реализации. В работе одновременно один основной этап. Отдельный небольшой проект выдаётся для проверки переноса навыка, когда Library перестаёт блокировать следующую тему.

## Основной проект: Library Backend

**Пользователь:** сотрудник небольшой библиотеки. **Задача:** вести каталог экземпляров, выдавать несколько книг одному читателю, принимать возврат и видеть текущие выдачи. Каждый Book — физический экземпляр с уникальным ID; одинаковые названия допустимы.

**Основа:** [существующий репозиторий ученика](https://github.com/Sulfurkino/Library). Не переписываем его целиком в готовый шаблон. Каждое изменение должно иметь понятную причину и проверку.

### Этап A — закончить текущий Core

**LIB-01. Поиск.** Устранить сортировку неизменяемого списка. Независимые необязательные фильтры по названию, минимуму/максимуму года и доступности; null отключает соответствующий фильтр. Название без учёта регистра, крайние пробелы игнорируются. Сортировка: год убывает, название и ID возрастают. Страница начинается с нуля, размер положительный; результат — элементы и total до разбиения. Ошибочные page/size/диапазон отклоняются.

Приёмка: семь совпадений при размере 3 дают 3/3/1/0 элементов с total=7; фильтры по отдельности и вместе; available=false; null; пустая/пробельная строка; отсутствие совпадений; каталог после поиска не изменён. Большие номера страниц — дополнительная проверка после обычных случаев.

**LIB-02. Проверка целостности.** Одна проблема на `(bookId, errorType)`; связанные readerId без повторений и по порядку. Сначала ID книги, потом тип ошибки. На одной книге возможны разные ошибки. Данные не исправляются самим валидатором.

Приёмка: один ID дважды у одного читателя; один ID у двух читателей; две разные книги у разных читателей; доступная книга у читателя; недоступная без читателя; книга вне каталога; сочетание нарушений. Дубликат отсутствующей книги даёт одну проблему отсутствия со всеми читателями и отдельную проблему повторной выдачи. Подсчёт вхождений не заменять подсчётом уникальных читателей.

**LIB-03. Контракты выдачи и ID.** Возвращать флаг и список причин отказа, не смешивая их с сообщениями об успешных проверках. Отказ не меняет состояние. При конфликте ID существующая книга не заменяется молча; новую запись отклонить с явным сообщением. Генератор ID не должен столкнуться с уже импортированной книгой.

Приёмка: из трёх книг одна занята — все состояния прежние; максимум пять книг; повтор ID; несуществующие читатель/книга; пустой/null запрос как ошибка; возврат только держателем; повторное добавление ID сохраняет прежнюю запись. Метод статистики и его расширенный вариант согласовать отдельно, не ломая необходимую вызывающему коду сигнатуру.

**LIB-04. Проверки и упаковка.** Перенести понятные ученику регрессионные сценарии в JUnit. README описывает JDK, сборку, проверки, модель и известные ограничения. Один небольшой PR/ветка на логически законченную задачу; не дробить каждую строку на PR.

Готовность этапа A: ученик показывает дефект на старой версии, объясняет исправление и проходит новый пример без готового ответа. Только после этого переход к веб-слою.

### Этап B — REST в памяти

Сначала прочитать: HTTP-запрос/ответ, JSON, статус; затем DI и Spring Boot. Учебная версия запускается локально. Версии JDK, Boot и зависимостей согласуются при создании стартового проекта по действующей документации; старые номера из курсов не копируются автоматически.

Минимальные операции:

- `POST /books` — добавить экземпляр; `POST /readers` — зарегистрировать читателя.
- `GET /books` — поиск с теми же фильтрами и страницами, что в LIB-01. Отсутствующий query-параметр отключает фильтр; строка `"null"` не имеет особого значения.
- `POST /readers/{readerId}/loans` с `{"bookIds":[1,2]}` — выдать книги одной операцией.
- `DELETE /readers/{readerId}/loans/{bookId}` — вернуть книгу указанного читателя.
- `GET /readers/{readerId}/loans` — текущие выдачи.

Согласованный учебный контракт: создание — 201; чтение — 200; успешный возврат — 204. Неверный формат/пустая заявка/неверная страница — 400; отсутствующий ресурс — 404; занятая книга, лимит или чужой возврат — 409. Ответ об ошибке содержит машинный код и понятный список причин. При сочетании ошибок приоритет: формат → существование → бизнес-условия; контракт закрепляется тестами.

Контроллер преобразует вход/выход, сервис выполняет правила, хранилище отвечает за данные. DTO поиска не позволяет изменить каталог. Swagger/OpenAPI и HTTP-примеры добавляются для воспроизводимой демонстрации, а не вместо тестов.

Приёмка: создать читателей и книги → найти страницу → выдать две книги → увидеть их у читателя → получить отказ при повторной выдаче → вернуть книгу правильным читателем → найти её доступной. На каждом отказе проверить состояние.

### Этап C — PostgreSQL и транзакции

Начать с ручной схемы и SQL на таблицах books/readers/loans, затем реализовать один путь через JDBC/JdbcTemplate. После понимания запросов перенести выбранный путь на JPA/Spring Data. Не держать две полноценные реализации хранилища как обязательную поддержку.

Выдача становится отдельной записью с ID экземпляра, ID читателя, временем выдачи и временем возврата. Название не уникально. Одна активная выдача относится к одному экземпляру. При переходе явно определить источник истины для доступности, чтобы флаг и активная выдача не расходились.

Даты/время вводить здесь на реальной задаче: что значит момент события и как он хранится. Ошибки валидатора Core остаются учебными сценариями на испорченных данных; ограничения БД не обходят ради демонстрации через публичный API.

Приёмка: после перезапуска выдача сохранена; схема поднимается миграциями; ошибка в середине операции не оставляет частичных изменений; два конкурентных запроса не выдают один экземпляр двум людям; лимит читателя защищён в транзакции. Последний конкурентный случай — отдельное занятие, не часть текущей двухпроходной проверки в памяти.

### Этап D — показать проект другому разработчику

Docker Compose запускает приложение и БД по README. Конфигурация не требует секретов в Git. Сохраняются unit-проверки правил и интеграционные проверки ключевых сценариев. Тестовая БД изолирована; повторный запуск не зависит от записей прошлого теста.

README содержит: задачу, способ запуска, схему данных, команды проверки, HTTP-примеры, принятые решения и ограничения. Ученик за 7 минут показывает проект и объясняет одну ошибку, один запрос SQL и одну транзакцию; затем за 15 минут меняет маленькое правило.

Сначала локальная воспроизводимая демонстрация. Доступ пользователей/роли и обработка 401/403 — отдельный следующий этап перед публичным доступом. Самостоятельная реализация JWT, платежи, фронтенд, Redis и микросервисы не входят в обязательный MVP.

### Дополнение после базовой готовности — события

На выдачу/возврат публикуется событие, учебный consumer строит уведомление или журнал. Проверить повтор одного eventId, недоступность consumer и повторную доставку. Обсудить разрыв между записью БД и отправкой события; не называть простой `save → send` гарантированной атомарностью. Это расширение Kafka из исходного плана, а не основание откладывать первые карьерные действия.

## Отдельный мини-проект: AccessLog Inspector

**Когда:** после принятия Core, вместо части обычной домашки. **Объём:** 3–4 часа на минимальный вариант; файлы/даты — ещё 1–2 часа только при доступном бюджете. **Зачем:** проверить те же коллекции и контракты на другой предметной области.

На вход подаётся список строк формата `timestamp;userId;path;status`, например:

```text
2026-10-01T10:00:00Z;anna;/books;200
2026-10-01T10:01:00Z;boris;/books;500
2026-10-01T10:02:00Z;anna;/loans;201
2026-10-01T10:03:00Z;anna;/books;404
broken
```

Версия 1 принимает `List<String>`; отдельный парсер возвращает разобранные события и ошибки с номерами строк от 1. Испорченная строка не прекращает разбор остальных. Null вместо списка — ошибка аргумента; null/пустая строка внутри списка — ошибка этой строки. Статус — целое число 100–599, userId и path непустые; временная метка разбирается как Instant после краткого знакомства с ним. Если даты ещё не изучены, этап парсинга дат выдаётся позже, а первый вход — готовые объекты событий.

Отчёт для каждого path содержит число запросов, число ответов 400–599 и отсортированные уникальные userId. Пути сортируются по числу запросов по убыванию, затем по строке по возрастанию. Входные данные не меняются; новые вызовы не накапливают предыдущий результат.

Ожидание для примера: `/books` — 3 запроса, 2 ошибки, пользователи `[anna, boris]`; `/loans` — 1 запрос, 0 ошибок, `[anna]`; ошибка разбора на строке 5. Пустой вход даёт пустой отчёт. Повтор одного пользователя увеличивает число запросов, но не список уникальных имён.

Приёмка: обычный пример; равные количества для разных путей; повтор пользователя; пустой ввод; все строки повреждены; одна плохая строка между хорошими; повторный запуск. Нужно уметь объяснить, почему Map/Set подходит каждому шагу.

Дополнение: читать UTF-8 файл через try-with-resources, различать ошибку открытия файла и плохую строку, сохранять отчёт. В учебном наборе нет настоящих пользовательских данных. CLI, Maven и JUnit подключаются постепенно, по уже изученным инструментам.

## Как принимаем проект

Для этапа ученик сдаёт код, короткое описание решений, примеры запуска и проверки. Наставник проверяет поведение, затем задаёт один вопрос «что изменится, если…» и даёт маленькое изменение требования. Защита входит в урок. Ассистент готовит условия, проверяет и объясняет; готовая реализация не подменяет самостоятельную работу ученика.
