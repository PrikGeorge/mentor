## 1. Выдача нескольких книг и возврат

**Что работает в проверенном коммите:** книги выдаются вместе; если одна из трёх занята, остальные тоже не выдаются. Проверки лимита в пять книг, отсутствующих книг и читателя, повторов ID и возврата правильным читателем прошли.

**Что доработать:** результат хранит причины отказа общей строкой. По заданию нужен признак успеха и **список причин**. Текст сообщения может оставаться для вывода, но вызывающий код должен получать отдельные причины, а не разбирать строку по разделителям.

**Пример для проверки:** читателя `999` нет; книга `2` занята; книги `999` нет; запрос — `[2, 2, 999]`. В сохранённой проверке объяснение содержит все четыре нарушения, но они представлены строкой. После доработки проверь, что причины можно прочитать как отдельные элементы списка и состояние библиотеки не изменилось.

**Критерий приёмки:** успешный результат содержит флаг успеха и пустой список причин отказа; при отказе — флаг отказа и отдельные причины. Сохрани проверку «из трёх книг одна занята — ни одна не выдана». `null` и пустой запрос должны оставаться ошибками без изменения состояния. В предыдущем наборе проверок исключение для таких входов допускалось; единый формат их представления согласуй с Георгием.

### Дополнительно: уникальность ID

При добавлении новой книги генератор может столкнуться с уже импортированным ID и заменить прежнюю книгу. Сохранённый пример: в каталоге есть книга `Imported` с ID `0`; после добавления `New` через менеджер по ID `0` находится уже новая книга, а размер каталога остаётся равным одному.

**Что проверить:** после импорта и добавления новой книги исходная запись сохраняется. Явное повторное добавление существующего ID должно отклоняться с понятным результатом; автоматически выбранный ID не должен конфликтовать с каталогом.

## 2. Отчёт по выданным книгам

**Что работает:** все 12 сохранённых проверок поведения прошли. Десятилетия и названия сортируются; разные экземпляры с одинаковым названием учитываются отдельно; имена читателей уникальны и отсортированы; пустой набор выдач даёт пустую карту.

**Пример:** у Анны — один экземпляр «Хоббита» 1937 года и «1984» 1949 года; у Бориса — другой экземпляр «Хоббита». Отчёт должен показывать два экземпляра «Хоббита» в 1930-х и один экземпляр «1984» в 1940-х. Совпадение названий не делает разные ID одной книгой.

**Что согласовать:** исходный контракт — `Map<Integer, Map<String, Long>>`. Сейчас вместо `Long` возвращается `BorrowedBookStat`, в котором можно хранить и количество, и имена. Это вопрос совместимости метода с условием, а не найденная ошибка подсчёта.

**Критерий приёмки:** либо сохраняешь обязательный метод с `Long` и добавляешь отдельный расширенный отчёт, либо явно согласуешь изменение API. Проверки количества и уникальных имён должны продолжать проходить. Если два читателя имеют одинаковое имя, имя в списке остаётся одно, но число их экземпляров всё равно учитывается полностью.

## 3. Проверка корректности учёта

**Что работает:** метод обнаруживает все четыре вида нарушений и не меняет данные библиотеки. Отдельно проверены повтор книги у одного читателя и возможность нескольких разных ошибок у одной книги.

**Что доработать:** результат должен сохранять связь конкретной книги с конкретными читателями. Сейчас некоторые проблемы объединяют несколько книг в одну запись; для отсутствующей книги, наоборот, могут появляться повторные записи одного типа.

### Пример А: две разные книги

Книга `30` дважды записана у читателя `1`, а книга `40` — дважды у читателя `16`.

Ожидаются две проблемы: дубль книги `30` с читателями `[1]` и дубль книги `40` с читателями `[16]`. В проверенном коммите получается одна проблема с книгами `[30, 40]` и читателями `[1, 16]`. Из неё уже нельзя понять, какая книга относится к какому читателю.

### Пример Б: отсутствующая книга у двух читателей

Книги `999` нет в каталоге, но она записана у читателей `1` и `16`.

Ожидаются две разные проблемы для книги `999`: повторная выдача и отсутствие в каталоге. В каждой — читатели `[1, 16]`. Сейчас отсутствие в каталоге описывается двумя отдельными записями, по одной на читателя.

### Пример В: порядок результата

Если нарушения относятся к книгам `1`, `2`, `3` и `100`, общий список должен идти именно в таком порядке независимо от типов ошибок. В сохранённой проверке получился порядок `[100, 2, 1, 3]`. Для связанных читателей `16` и `1` ожидается `[1, 16]`, без повторений.

**Критерий приёмки:** одна запись на пару «ID книги + тип ошибки», все относящиеся к ней читатели уникальны и отсортированы. Весь результат отсортирован сначала по ID книги, затем по типу ошибки. Одна книга может иметь несколько разных ошибок. Проверь эти правила одновременно на намеренно испорченном наборе; каталог, списки и флаги после вызова должны остаться прежними.

**С чего начать:** для каждой книги отдельно подготовь число вхождений и связанных читателей. Повтор у одного читателя тоже считается нарушением: один уникальный читатель не означает одно появление книги.

## 4. Поиск с фильтрами и страницами

**Что работает без фильтров:** порядок книг, обычные страницы и общее количество совпадений. Отрицательная страница, неположительный размер и обратный диапазон годов отклоняются. `BookView` больше не предоставляет setters, а результаты поиска не позволяют изменить каталог.

**Первый блокирующий дефект:** обычный включённый фильтр приводит к `UnsupportedOperationException` при сортировке. После `Stream.toList()` получается неизменяемый список, а `sort` пытается изменить порядок элементов в этом списке. В сохранённом наборе 15 падений имеют одну эту причину; это не 15 разных ошибок фильтрации.

**Твоя проверка:** вызови поиск с непустой частью названия, затем отдельно с нижней границей года, верхней границей и доступностью. Сохрани падающий сценарий до правки. После исправления каждый вызов должен вернуть подходящие книги в требуемом порядке, а не упасть на сортировке. Пока этот дефект есть, нельзя считать поведение всех фильтров подтверждённым.

**Второй дефект:** настоящий `null` в отдельном поле вызывает `NullPointerException` на вызове `isPresent()`. По условию `null` должен отключать только этот фильтр. Если сохраняешь параметры типа `Optional`, проверь отдельно `Optional.empty()` и `null`: это разные входы.

**Твоя проверка:** название равно `null`, но минимум года включён — должен работать только фильтр года. Повтори для каждого поля, а затем отключи все фильтры через `null`. Для названия отдельно сравни `"  jaVa  "` и `"java"`; пустая строка и одни пробелы не должны ограничивать поиск.

**Третий дефект, после обычных случаев:** на очень больших положительных номерах страниц произведение `page * pageSize` переполняет `int`. В сохранённых сценариях это приводило либо к отрицательному индексу, либо к выдаче первой страницы вместо пустой. Отдалённая страница должна оставаться пустой и сохранять `total`.

**Критерий приёмки:** фильтры работают по отдельности и вместе; границы года включительны; сортировка — год по убыванию, затем название и ID по возрастанию. Для семи совпадений и размера страницы 3 страницы 0–3 содержат соответственно 3, 3, 1 и 0 элементов, а `total` в каждом ответе равен 7. Повторный поиск не меняет каталог.
