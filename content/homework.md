## Шаг 1. Поиск и регрессионные проверки — 80–110 минут

Доведи исправление сортировки в рабочей Library. Затем выполни исходный контракт отсутствующих фильтров: **настоящий `null` в отдельном поле отключает соответствующий фильтр**. Пустая строка названия и строка из пробелов после `trim()` тоже не ограничивают поиск. `null` и `Optional.empty()` нужно проверить отдельно при сохранении текущей сигнатуры. Не добавляй условие, что вызывающий код обязан заменить каждый `null` заранее.

Дополнять четырьмя новыми возможностями поиск не нужно. Выбери понятную реализацию существующего контракта; способ обращения с текущими `Optional` обсуди с преподавателем при необходимости.

Сохрани воспроизводимые проверки — существующий тестовый запуск проекта или небольшой проверяющий `main`, который сообщает о несовпадении ожидаемого и фактического результата. Входы задавай явно. Проверь:

- Каждый из четырёх фильтров включён отдельно: название, нижняя граница года, верхняя граница года, доступность. Сортировка не падает.
- Каждый фильтр равен настоящему `null`, а другой фильтр активен. Отключается только соответствующее ограничение; вызов не падает. Также проверь четыре `null` одновременно.
- Название `"  jaVa  "` даёт тот же отбор, что `"java"`; `""` и `"   "` не ограничивают поиск.
- Несколько совпадений, одно совпадение и ни одного совпадения.
- Сортировка при равных годах и названиях; две страницы и страница за концом результата. `total` — число всех совпадений до разбиения на страницы.

Для точной проверки порядка и страниц возьми отдельный каталог: `40/Alpha/2020`, `10/Beta/2020`, `20/Alpha/2020`, `30/Zulu/2022`. При отключённых фильтрах порядок ID должен быть `[30, 20, 40, 10]`. При `pageSize=2`: страница 0 → `[30,20]`, страница 1 → `[40,10]`, страница 2 → `[]`; во всех трёх вызовах `total=4`. После вызовов данные каталога остаются прежними.

Критерий готовности: можешь показать старое падение, объяснить причину изменения и запустить сохранённые проверки. Если срок закончился раньше, приложи конкретные непрошедшие случаи, без отметки «готово».

## Шаг 2. Данные для проверки по каждой книге — 50–70 минут

Заверши `GroupingTask`, если не успел на уроке. Затем в своей Library подготовь промежуточные сведения по `bookId`: число появлений в списках читателей и набор связанных ID читателей. Вход здесь берётся из настоящих `Reader.getBooks()`. Не смешивай сведения разных книг и не удаляй повторы до подсчёта.

Минимальный результат этой части: промежуточные карты и воспроизводимые случаи «дважды у одного читателя», «у двух читателей», «две разные книги» и «одна запись». Покажи, как из них получится одна проблема типа «дубль» на книгу, а читатели будут уникальны и отсортированы. Сортировку нужно задать явно; порядок `HashSet`/`HashMap` не является критерием правильности.

Если время осталось, перенеси в `validateLibrary` **только правило дублей** и проверь его. Существующий `LibraryProblem` может хранить множество с одним ID книги; переделка всех классов результата не требуется. Для остальных типов пока достаточно описать ожидаемый результат: две отсутствующие в каталоге книги должны дать отдельные проблемы, а повтор одной отсутствующей книги у разных читателей — одну проблему этого типа со всеми её читателями. Остальные правила разберём на следующем занятии.

## Шаг 3. Подготовить сдачу — 15–30 минут

Принеси код, способ запуска проверок, фактический вывод, затраченное время и один вопрос. В заметке из 5–8 предложений объясни причину ошибки со списком, выбранное исправление, разницу между числом выдач и числом читателей, готовую часть валидатора и оставшийся шаг.

Если застрял на одном месте на 20 минут, зафиксируй вход, ожидание, фактический вывод и гипотезу. Переходи к заметке для преподавателя, не выходи за общий лимит времени.

**Дополнительно, только после обязательного и в пределах лимита:** исследуй `page * pageSize` на очень больших положительных значениях. Опиши риск переполнения `int`, предложи проверку и способ сохранить правильное поведение страницы за концом результатов. Это не обязательная часть ближайшей сдачи.
